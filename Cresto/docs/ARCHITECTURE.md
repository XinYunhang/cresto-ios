# 架构与路线（讨论稿）

## 1. 定位

一个只给自己用的 iOS App：**待办 + 今日运势 + 塔罗 + 使用热力图**，后期接 **dsh 远程**。
所以三条原则：

- **单机优先**，没有后端。数据落本地，用 iCloud 私有库同步，不需要服务器和账号体系。
- **可选 AI**，不是必需依赖。没网、没配 Key 也必须能用。
- **手写 SwiftUI**。这套毛玻璃浮动底栏、卡片节奏，跨端框架做不出味道，而且你只有一个平台。

## 2. 技术栈

| 层 | 选择 | 理由 |
| --- | --- | --- |
| UI | SwiftUI（iOS 17+） | `@Namespace` + `.ultraThinMaterial` 刚好够做这套底栏 |
| 持久化 | SwiftData | 对标 Cresto 的 Room；`@Model` 直接进 `@Query` |
| 同步 | CloudKit 私有库 | 自己的多台设备够用，零运维 |
| 通知 | UserNotifications 本地通知 | 不依赖服务端 |
| AI | OpenAI 兼容 HTTP（可自定义 baseURL / model） | 和 Cresto 一样的思路，Key 存 Keychain |
| 终端（后期） | SwiftTerm + NIO SSH | iOS 上唯一现实的远程方案 |

## 3. 信息架构

底部栏：**4 个 tab + 独立 FAB**（一个胶囊 + 一个圆按钮，中间留 11pt 空隙）。

```
概览  |  待办  |  塔罗  |  时间          ( + )
```

- **概览**＝首页：运势卡 → 今日待办 → 塔罗摘要 → 使用时间摘要。四个功能域在这里各露一块，互相导流。
- **FAB**＝快速添加，拉半屏卡片 + 键盘，和待办页共用同一个 Sheet。
- **dsh 入口**先放在概览页头右上角的 `terminal` 图标（带在线绿点）。等真做出来再决定要不要升成第 5 个 tab——那时胶囊变 5 格，FAB 保留。
- 运势没有独立 tab：它天生是「今天」的摘要，放概览里最合适；详情页走 push。

## 4. 数据模型

```swift
@Model TaskItem   // 标题、备注、dueDate、hasTime、优先级、提醒偏移、重复规则、标签、seriesId、软删除
@Model Subtask    // 归属 TaskItem，cascade 删除
@Model Course     // 课程名、教师、地点、灰阶档位
@Model CourseSlot // 星期 / 起止节次 / 起止周 / 单双周 -> 一门课可以有多个时段
@Model TimetableSettings // 开学日期、节次数量、每节开始时间（单例）
FortuneDay        // 日期(唯一)、分数、四维指标、关键词、宜/忌、AI 文案（未接）
TarotDraw         // 每日一抽 (struct，未落库)
UsageEntry        // 日期(唯一)、分钟数、level(0...4)、来源（未接）
```

`FortuneDay` 和 `TarotDraw` 都以「日期」为唯一键：**一天只生成一次，缓存住，重开 App 结果不变**。这是运势类功能的基本体面。

## 5. 三个需要你拍板的决策

### 5.1 热力图的数据从哪来（最大的坑）

「使用时间」有三种理解，成本和可行性差很多：

| 方案 | 可行性 | 得到什么 |
| --- | --- | --- |
| A. 系统屏幕使用时间（Screen Time API） | **难**。要 `com.apple.developer.family-controls` 权限，需向 Apple 单独申请，个人开发者账号基本拿不到；拿不到只能自签开发机跑 | 全设备真实使用时长 |
| B. App 内专注计时 / 活跃度 | **易**，完全可控 | 待办完成数 × 专注时长，反映"你在这套系统里的产出" |
| C. 手动或截图导入 | 易，但没人坚持 | 数据质量最差 |

**建议先做 B**，但数据层别锁死：`UsageEntry` 存的是「某天的分钟数 + level + 来源」，将来换成 Screen Time Provider 只改采集层，视图一行不用动。
热力图本身的视觉（周一在上、按周分列、5 级色阶）三种数据源通用。

### 5.2 运势 / 塔罗的 AI 怎么用

拆成「**本地抽签 + AI 润色**」两层，而不是让模型直接决定结果：

- **运势**：用 `hash(日期 + 用户生辰/生肖)` 做种子 → 从本地表里取分数、关键词、宜忌。**同一天刷新多少次都一样**，离线也成立。AI 只负责把这几项写成一段人话（失败就回落到模板文案）。
- **塔罗**：78 张牌库是本地 JSON，抽牌用 `SystemRandomNumberGenerator`（真随机，不复现）。AI 只做解读，prompt 里塞：牌名、正逆位、你的问题、最近 7 天待办完成情况。
- 配置项照抄 Cresto：baseURL + API Key + model，Key 进 Keychain，可一键关掉 AI。

### 5.3 dsh 远程在 iOS 上是什么形态

**先说结论：iOS 端做不了 dsh-go 的「本机运行」那一半。**
dsh-go 是 Flutter + Android 的 PRoot 方案，在手机里装 Ubuntu + Node 跑 DSH。iOS 沙盒没有 fork/exec、没有 PRoot、没有 JIT，这条路走不通。**但你要的是「远程接管」，这半边完全可行**：

1. **SSH 到你的电脑/服务器**（推荐第一版）：`SwiftTerm` 做终端渲染（MIT），`Citadel`/NIO-SSH 做连接。功能＝连接管理 + 终端 + 快捷命令。
2. **DSH Remote 插件协议**（进阶）：如果它走 WebSocket，就做原生会话界面，比终端体验好，但要跟着它的协议版本跑。

两个 iOS 专属坑：
- 退到后台 → 连接会被挂起，回来要断线重连（监听 `scenePhase`）。
- 不要试图把长任务放前台等，改成「发出去 → 通知里看结果」。

## 6. 从 Cresto 值得抄的部分

| Cresto（Android） | 这里对应 |
| --- | --- |
| Room + 版本化 schema | SwiftData，`VersionedSchema` |
| Glasense 液态玻璃设计系统 | 现在的 `Theme` + `GlassTabBar`，只是先做暗色单主题 |
| 一句话/截图 AI 抽出待办 | **很值得做**：Share Extension + 一个"文本 → 待办"的入口 |
| Shizuku 抓屏 | iOS 没有，用 Share Extension / 快捷指令替代 |
| Insights 页 | 我们的「时间」页可以顺手把待办完成率放进去 |
| JSON 导入导出 | 直接做，个人数据必须能自己拿走 |

## 7. 路线

- **P0（已完成）**：主页视觉 + 底栏 + 页面骨架 + 假数据。
- **P1（已完成）**：SwiftData 落地待办（日期+时间、提醒、优先级、标签、子任务、重复）、编辑页、本地通知、课表（周视图 + 课程编辑）。
- **P1.5（已完成）**：课表图片导入（Vision 认字 + 坐标落格 + 人工校对）、22 张塔罗真数据与每日一抽落库。
- **P1.6（下一步）**：运势接确定性种子、热力图接真实采集、课表小组件、最近删除。
- **P2**：运势 + 塔罗接真实现（本地种子 + 牌库 + AI 解读 + 每日缓存）。
- **P3**：时间页接真实采集（先专注计时），热力图接数据。

## 7.1 课表导入为什么选了图片识别而不是 ICS

需求方手上的课表是一张图表截图，不是 ICS 文件；而教务系统千校千面，抓门户（LightTable 的做法）维护成本最高。
所以取中间路线：把截图交给 Vision 认字，再用「周一…周日」定位列、左侧节次定位行、按坐标把课名落格，最后给一个可逐条修改的核对页。
识别错几条是可以接受的，因为校正成本远低于手动录入；但如果以后要批量导入，仍然优先做 ICS / Excel 解析，别继续加 OCR 规则。
- **P4**：dsh 远程（SSH 终端 → 会话界面），后台重连。

## 8. 工程约定

- 一个 `Theme` 管所有颜色/圆角/间距，不允许视图里写死色值。
- 卡片一律走 `.cardSurface()`，保证描边、渐变、圆角一致。
- 页面结构统一：`ScrollView` + `VStack(spacing: 10)` + `padding(.bottom, 132)`（给浮动底栏留位）。
- 所有图标用 SF Symbols，不引入图标库。
